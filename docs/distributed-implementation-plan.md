# Distributed Mingle implementation plan

## Product rules

Local agents remain the default. Merely linking a computer, joining a team, adding a remote agent, or seeing an idle remote provider never starts inference or transfers work. Remote execution is exceptional: a recorded quota-exhausted/provider-unavailable failure or an explicit human-requested recovery of unpublished work is required. Suggestions do not execute. The destination device owner must approve the exact request, project binding, agent/model, quota spend and operation before execution. A team owner cannot approve on another device owner's behalf. Push/merge and command execution have separate approvals. Unknown quota is unknown, never available.

Mingle accounts authorize team membership using verified account UUIDs, never display names. Provider credentials stay on their own devices. The existing loopback HTTP server is never exposed to a network. Devices use outbound authenticated cloud mailbox requests, so NAT and different networks require no inbound ports. Device-to-device payloads are encrypted and authenticated; enrollment requires explicit fingerprint verification. Revoking a member/device/link prevents future messages and invalidates pending execution authority.

## Six implementation workers and ownership

1. Accounts/teams: `apps/server/src/distributed/teams.ts`, `teams.test.ts`, `packages/contracts/src/teams.ts`, `supabase/migrations/*`, account service's server-only authenticated-client bridge. Team membership, expiring invitations, shared projects and mailbox/device cloud tables with RLS. No cloud deployment.
2. Device transport: `apps/server/src/distributed/transport*`, `crypto*`, `packages/contracts/src/devices.ts`. Private local device keys, registration, fingerprint-pinned pairing/revocation, E2E encrypted durable mailbox, SQLite outbox/inbox, retry/replay protection, reconnect and honest presence.
3. Remote execution: `apps/server/src/distributed/execution*`, `packages/contracts/src/remote-execution.ts`. Durable owner-local approvals, exceptional eligibility, remote agent roster, delegation, provider/quota failure handoff, at-most-once execution and unknown-outcome recovery. Runtime injection, no direct provider credential access.
4. Git/commands: `apps/server/src/distributed/git*`, `commands*`, `packages/contracts/src/remote-git.ts`. Git bundle handoff of unpublished commits, fingerprint-bound approvals, safe argv-only restricted commands, conflict inspection, explicit push/merge review, audited outcomes. No ordinary remote shell.
5. UI: `apps/web/src/components/distributed/*`, `styles/distributed.css`, Settings/store integration, shared agent map UI. Team workspace, invitations, device linking, shared project binding, agents, conversations, tasks, approvals, fallback proposals, Git transfers and truthful offline/errors. Use existing components/styles.
6. Verification: `apps/server/src/distributed/integration.test.ts`, `docs/distributed-workspaces.md`, `supabase/tests/*`. Cross-account and two-device protocol/adversarial tests, recovery scenarios, deployment/runbook and limitations. No paid model tests.

Orchestrator owns `apps/server/src/app.ts`, `routes.ts`, main MCP wiring, contracts `index.ts`, shared top-level configuration, final integration and validation. Every worker gets an isolated worktree at this base, commits only owned paths and reports its commit and API. No push, publication, installation or production cloud migration.

## Common integration APIs

Each module exports a service class accepting a single options object, with dependency injection for tests. Services share the existing `Store.db` SQLite connection; their constructors may idempotently create namespaced tables. Cloud work goes through `AccountService.withAuthenticatedClient(async (client, user) => ...)`, verifying `auth.getUser` server-side on every authority-sensitive operation and never returning tokens to the renderer.

TeamService: constructor `{account, changed}`. `snapshot()`, `createTeam({name})`, `invite({teamId,email,role})`, `acceptInvite({token})`, `revokeMember({teamId,userId})`, `createProject({teamId,name,repositoryUrl})`, `assertMember(teamId)` and `withClient(callback)`; exact return types published by worker. Cloud tables prefixed `mingle_`. Device and relay SQL coordinated by the blueprint below. Invitations are shareable, expiring one-time secrets shown only at creation, hashed in storage. Invite acceptance verifies target email against verified account identity. Share invitation yourself; no email service is implied.

TransportService: constructor `{account, store, dataDir, changed}`. `snapshot(teamId?)`, `register({teamId,name})`, `link({teamId,deviceId,fingerprint})`, `revoke({teamId,deviceId})`, `send({teamId,toDeviceId,kind,payload,idempotencyKey})`, `onMessage(handler)` returning unsubscribe, `sync()`, `close()`. It maintains a local device identity. `onMessage` receives authenticated `{id,teamId,fromDeviceId,toDeviceId,kind,payload}`. Handler failures must not lose messages. No incoming payload executes before execution service checks authorization. Local UI/API never accepts a peer's asserted owner ID as authority.

Cloud tables owned by worker 1, compatible with worker 2: `mingle_teams(id,name,owner_id,created_at)`; `mingle_members(team_id,user_id,role,created_at)`; `mingle_invitations(id,team_id,email,role,token_hash,expires_at,accepted_at,created_at)`; `mingle_projects(id,team_id,name,repository_url,created_at)`; `mingle_devices(id,team_id,owner_id,name,signing_public_key,encryption_public_key,fingerprint,last_seen_at,revoked_at,created_at)`; `mingle_device_links(team_id,device_id,peer_device_id,peer_fingerprint,created_at)` with explicit unilateral trust pin (both sides required before delivery); `mingle_envelopes(id,team_id,from_device_id,to_device_id,idempotency_key,kind,ciphertext,nonce,signature,created_at,expires_at)` unique sender/recipient/key. Supabase RLS verifies active membership, both devices and mutual links; sender owns from-device, recipient owns to-device. Client-supplied timestamps cannot extend trust indefinitely. Transport worker may request additive columns via its report; do not mutate another worker's files.

RemoteExecutionService: constructor `{store,account,transport,runtime,workspace,providers,changed}`. `snapshot(teamId?)`, `bindProject({teamId,sharedProjectId,localProjectId})`, `publishAgents({teamId,sharedProjectId,sessionIds})`, `suggestFallback(...)`, `requestDelegation(...)`, `decide({requestId,decision})`, `onEnvelope(envelope)`, `close()`. It validates membership and both local/remote project binding on every mutation, pins approvals to immutable request digests and device/account owner, consumes grants once, reserves session locks before invoking existing `SessionRuntime.send` API (inspect actual runtime method), persists dispatch before starting, never retries uncertain dispatched work after restart. Explicit allowlisted agent roster; no arbitrary remote session creation. Distributed group IDs and dependencies must be visible in snapshots; publish shared messages/results through transport kinds `execution.*`/`collaboration.*`. The existing local groups should be able to propose a remote delegation via a scoped team MCP tool, without bypassing owner approvals or exceptional eligibility.

GitSyncService and RemoteCommandService: constructors with `{store,account,transport,workspace,repository,changed}` and injected executors as needed. Own payload kinds `git.*` and `command.*`; publish snapshot/request/decide/onEnvelope APIs for orchestrator. Bind every operation to shared project/device and immutable request digest. Never execute an incoming filesystem path or Git URL supplied by a peer. Git bundles import into isolated refs/worktrees, never checkout over working edits. Bound size/time/output, block hooks/external helpers/unsafe configs. Commands are structured allowlisted executable + argv, scoped to owner-bound project, no shell or arbitrary scripts/exec interpreters. Treat this as restricted process execution, not an OS sandbox.

## HTTP/UI integration

All local routes remain guarded by existing Host/Origin protections and live under `/api/distributed`. The orchestrator wires services and HTTP routes after merging. For UI development use an isolated `distributed/api.ts` with typed `request` wrapper and these routes:

- GET `/snapshot?teamId=...` -> `{teams,transport,execution,git,commands}` (each is its service snapshot).
- POST `/teams` `{name}`, `/invitations` `{teamId,email,role}`, `/invitations/accept` `{token}`, `/members/revoke` `{teamId,userId}`, `/projects` `{teamId,name,repositoryUrl}`.
- POST `/devices/register` `{teamId,name}`, `/devices/link` `{teamId,deviceId,fingerprint}`, `/devices/revoke` `{teamId,deviceId}`, `/sync` `{}`.
- POST `/projects/bind` `{teamId,sharedProjectId,localProjectId}`, `/agents/publish` `{teamId,sharedProjectId,sessionIds}`.
- POST `/delegations`, `/fallbacks/suggest`, `/approvals/:id` `{decision:'approved'|'denied'}`.
- POST `/git/request`, `/git/:id/decision`, `/commands/request`, `/commands/:id/decision`.
- POST `/messages` shared conversation submission; GET `/snapshot` includes durable conversation messages, tasks, agents, approvals and timeline.

Parent adapts request bodies to final service schemas; UI worker must document fields it uses. Responses/errors truthful: missing cloud migration/sign-in/offline are explicit, with no manufactured devices, agents or quota. Existing local flows remain usable when distributed services are unavailable. UI can poll snapshot at a bounded cadence while open and rely on existing state-change WebSockets for refresh hints.

## Validation and release gates

Focused no-model tests must cover nonmember access, invitation replay/expiry/wrong account, device pin mismatch/revocation, ciphertext tampering, duplicate delivery, out-of-order/reconnect, approval replay/other-owner decisions/payload mutation, local-first eligibility, stale/unknown quota, dispatched-crash uncertainty, Git unpushed commits/conflicts/branch validation and command escape rejection. Run workspace typecheck, backend suite and production build after integration. SQL is checked locally when a PostgreSQL test instance is available; report absence rather than claim RLS verified. Device/cloud deployment and actual provider runs require separate validation, never fabricated.
